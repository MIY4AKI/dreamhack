## 1. 프로그램과 프로세스

**프로그램**은 저장 장치에 있는 코드와 파일이고, **프로세스(Process)**는 실행되고 있는 프로그램의 인스턴스입니다. 강의의 비유로 프로그램은 요리 레시피, 프로세스는 그 레시피대로 실제로 요리하는 과정입니다.

사용자 또는 다른 프로세스가 실행을 요청하면 운영체제는 필요한 실행 상태를 구성합니다. 프로그램은 메모리에 매핑·적재되어 CPU에서 명령을 실행합니다. 여러 프로세스가 있으면 운영체제의 스케줄러가 실행 순서를 조절합니다.

`ls`, `find`, `mkdir` 같은 명령도 프로그램이며 실행 중에는 프로세스입니다. 다만 `cd` 등 셸 내장 명령은 셸 자체가 처리할 수 있으므로 모든 명령이 별도 실행 파일인 것은 아닙니다.

## 2. 상태와 부모·자식 관계

### 강의의 5가지 상태 모델

- **생성(Create)**: 프로세스가 만들어지는 중.
- **준비(Ready)**: 실행할 수 있지만 CPU를 기다리는 중.
- **실행(Running)**: CPU를 사용하여 명령 실행 중.
- **대기(Blocked)**: 입력·출력이나 자원 등의 조건이 충족되기를 기다리며 CPU를 양도한 상태.
- **종료(Terminated)**: 실행을 마치는 상태.

강의의 상태 전이도는 생성 후 준비, CPU를 배정받아 실행, 필요에 따라 준비나 대기로 이동, 조건이 충족되면 다시 준비, 실행 완료 후 종료되는 관계를 보여줍니다. 이는 일반적인 개념 모델이며 `ps`의 상태 문자는 아래처럼 더 세분화됩니다.

### PID / PPID, fork / exec

- **PID(Process ID)**: 현재 프로세스를 식별하는 번호. 같은 PID 네임스페이스에서 살아 있는 프로세스를 구별합니다.
- **PPID(Parent Process ID)**: 부모 프로세스의 PID.
- `fork()`: 현재 프로세스를 기반으로 자식 프로세스를 생성합니다.
- **부모(Parent)**: 자식을 생성한 프로세스.
- **자식(Child)**: 새로 생성된 프로세스.
- `exec()` 계열: 현재 프로세스의 실행 이미지를 다른 프로그램으로 교체합니다. `exec` 자체가 새 PID의 프로세스를 만드는 것은 아닙니다.

셸이 외부 프로그램을 실행하는 전형적인 방식은 **자식 생성 → 자식에서 exec → 다른 프로그램 실행**입니다. 강의는 프로세스 트리의 최상위 사용자 공간 프로세스를 `init`, PID 1로 소개합니다. 현대 배포판에서는 그 역할을 systemd 등이 맡을 수 있습니다.

### 고아와 좀비

- **고아 프로세스(Orphan)**: 부모가 먼저 종료되어 부모 관계를 다시 설정해야 하는 자식.
- **좀비 프로세스(Zombie)**: 자식은 종료했지만 부모가 아직 종료 상태를 수거하지 않은 상태.
- 부모는 자식 종료를 인지하고 종료 상태를 수거할 책임이 있습니다. 정상적인 경우에도 종료와 수거 사이에 잠깐 좀비 상태가 생깁니다.
- 강의는 고아의 부모가 PID 1로 바뀌는 기본 모델을 설명합니다. 실제 환경에는 subreaper나 PID 네임스페이스 등 추가 조건이 있으므로 언제나 호스트 PID 1이라고 단정하지 않습니다.

## 3. ps로 상태 확인

`ps [옵션]`은 현재 프로세스 정보의 스냅샷을 보여줍니다. 반복적으로 갱신하는 모니터는 `top`이나 `htop`입니다.

### 강의에 등장하는 옵션

- `-A`, `-e`: 모든 프로세스 선택.
- `-a`: 세션 리더와 터미널에 연결되지 않은 프로세스를 제외하여 선택.
- `-f`: full format.
- `-l`: long format.
- `-M`: 보안 정보 열 추가(SELinux 컨텍스트 등).
- `-m`: 프로세스 뒤에 스레드도 표시.
- `-p PID`: 지정한 PID 선택.
- `-u 사용자`: 지정한 유효 사용자 ID/이름의 프로세스 선택.
- `r`: 실행 중 또는 실행 가능한 프로세스 선택. BSD 형식으로 대시 없이 씁니다.

> **강의 옵션표 정정:** Linux procps의 `-e`는 커널 프로세스를 제외하는 옵션이 아니며 `-A`와 같습니다. `-a`는 터미널 없는 프로세스를 제외합니다. `-M`은 64비트 필터, `-m`은 커널 스레드만의 필터가 아닙니다. 강의의 `-r`도 구현별 옵션 문법을 확인하고, 여기서는 매뉴얼의 `r`을 사용합니다. [procps ps 매뉴얼](https://man7.org/linux/man-pages/man1/ps.1.html)

### 출력 열 읽기

- `F`: 프로세스 플래그. 강의의 비트 값 1은 fork 후 아직 exec하지 않은 상태, 4는 슈퍼유저 권한을 사용한 이력에 대응합니다.
- `S` / `STAT`: 상태 코드.
- `UID`: 사용자 ID.
- `PID`, `PPID`: 자신과 부모의 프로세스 ID.
- `C`: CPU 사용률 관련 값.
- `PRI`: 스케줄링 우선순위.
- `NI`: nice 값.
- `SZ`: 가상 메모리 크기 관련 값.
- `WCHAN`: 잠들어 기다리는 커널 함수/대기 위치.
- `TTY`: 연결된 터미널.
- `TIME`: 누적 CPU 사용 시간. 실행한 뒤 지난 벽시계 시간과 다릅니다.
- `CMD`: 실행 명령.

주요 상태 코드는 다음과 같습니다.

- `R`: 실행 중 또는 실행 가능.
- `S`: 인터럽트 가능한 휴면, 이벤트 대기.
- `D`: 인터럽트 불가능한 휴면, 주로 I/O 대기.
- `I`: 유휴 커널 스레드.
- `T`: 작업 제어 시그널로 정지.
- `t`: 디버거의 추적 중 정지.
- `X`: 죽은 상태.
- `Z`: 종료했으나 수거되지 않은 좀비.

### 입력을 기다리는 프로그램 실습

`ps_test.c`:

~~~c
#include <stdio.h>

int main(void) {
    setvbuf(stdout, 0, 2, 0);
    printf("input: ");
    getchar();
    printf("finish\n");
}
~~~

~~~bash
gcc -o ps_test ps_test.c
./ps_test
~~~

다른 터미널에서 자신의 계정 이름을 사용합니다.

~~~bash
ps -u user -l
~~~

- `getchar()`에서 입력을 기다리는 `ps_test`는 예제에서 `S`입니다.
- `ps_test`와 `ps`를 서로 다른 터미널에서 실행했으므로 TTY도 다릅니다.
- 프로그램 터미널에서 **Ctrl+Z**를 누르면 종료가 아니라 정지이며, `T` 상태로 바뀝니다.

## 4. 포그라운드·백그라운드와 jobs

**포그라운드(Foreground)** 작업은 해당 터미널에서 사용자 입력과 직접 상호작용합니다. **백그라운드(Background)** 작업은 셸이 다음 명령을 받을 수 있도록 뒤에서 동작합니다. 백그라운드라고 반드시 멈춘 상태는 아니며, 백그라운드 프로세스도 표준 출력을 터미널에 쓸 수 있습니다.

- `jobs`: 현재 셸이 관리하는 작업의 번호와 상태 확인.
- `fg %1`: 작업 1을 포그라운드로 가져오고, 정지했다면 재개.
- `bg %1`: 정지한 작업 1을 백그라운드에서 재개.
- `명령 &`: 처음부터 백그라운드 실행.

강의의 `fg 1`, `bg 1`은 작업 번호 1을 다루는 예입니다. `%1`처럼 작업 지정임을 명확히 쓰면 PID와 혼동하지 않기 쉽습니다. 작업 번호는 셸 내부의 번호이며 PID와 다릅니다.

`ps_test`를 백그라운드로 보냈더라도 터미널 입력을 읽으려 하면 다시 정지할 수 있습니다. 이는 단순히 입력 대기 `S`와 같은 상태가 아니라 백그라운드 터미널 읽기에 대한 작업 제어의 결과입니다.

### 실행 중인 백그라운드 작업 보기

`infinite_loop.c`:

~~~c
#include <stdio.h>

int main(void) {
    while (1);
}
~~~

~~~bash
gcc -o infinite_loop infinite_loop.c
./infinite_loop &
jobs
ps -u user -l
~~~

- 셸은 `[작업번호] PID`를 출력합니다.
- `jobs`에서 Running, `ps`에서 `R`인 모습을 볼 수 있습니다.
- 정지된 `ps_test`가 남아 있다면 작업이 두 개 보일 수 있습니다.

> 무한 루프는 CPU를 계속 사용합니다. 격리된 실습 환경에서만 사용하고, 관찰을 마친 뒤 **자신이 만든 해당 PID**를 확인하여 종료하세요.

## 5. 시그널과 종료

**시그널(Signal)**은 프로세스에 이벤트를 알리는 비동기 통지입니다. `kill`은 이름과 달리 종료만이 아니라 다양한 시그널을 전송합니다. 기본 종료 요청은 SIGTERM입니다.

형태: `kill -시그널 PID`. `kill -l`로 이름과 번호를 확인합니다.

강의의 번호 예시는 일반적인 Linux x86 계열을 기준으로 읽습니다. 아키텍처에 따라 번호가 달라질 수 있습니다. 다음의 ‘종료·코어’는 기본 동작을 뜻하며 프로세스의 핸들러 설정 등에 따라 달라질 수 있습니다.

- 1 `SIGHUP`: 터미널/연결 종료 등의 통지 — 종료.
- 2 `SIGINT`: Ctrl+C 등의 인터럽트 — 종료.
- 3 `SIGQUIT`: 종료 요청 — 종료 및 코어 덤프.
- 4 `SIGILL`: 잘못된 명령 실행 — 종료 및 코어 덤프.
- 5 `SIGTRAP`: 트랩·디버거 중단점 — 종료 및 코어 덤프.
- 6 `SIGABRT`: `abort()` 등의 비정상 종료 — 종료 및 코어 덤프.
- 7 `SIGBUS`: 잘못된 메모리 접근 등의 버스 오류 — 종료 및 코어 덤프. 정렬 문제는 가능한 원인 중 하나입니다.
- 8 `SIGFPE`: 잘못된 산술 연산 — 종료 및 코어 덤프.
- 9 `SIGKILL`: 강제 종료 — 종료. 핸들러로 처리하거나 무시할 수 없습니다.
- 11 `SIGSEGV`: 접근할 수 없는 메모리 참조 — 종료 및 코어 덤프.
- 13 `SIGPIPE`: 읽는 쪽이 없는 파이프 등에 쓰기 — 종료.
- 14 `SIGALRM`: `alarm()` 등 타이머 만료 — 종료.
- 15 `SIGTERM`: 정상적인 종료 요청 — 종료.
- 17 `SIGCHLD`: 자식의 종료·정지 등의 상태 변화 통지 — 기본적으로 무시.
- 19 `SIGSTOP`: 정지 — 핸들러로 처리하거나 무시할 수 없습니다.
- 31 `SIGSYS`: 잘못된 시스템 호출 — 기본 동작은 종료 및 코어 덤프.

> 보충: 모든 시그널을 “즉시 기존 작업을 중단하여 반드시 처리한다”고 단정하면 안 됩니다. 일부는 차단·무시·사용자 핸들러 처리가 가능하고, SIGKILL/SIGSTOP은 예외입니다. SIGSYS의 코어 덤프 기본 동작도 함께 보충했습니다. [Linux signal 매뉴얼](https://man7.org/linux/man-pages/man7/signal.7.html)

실습 종료는 실제 PID를 확인한 뒤 먼저 `kill PID`로 요청합니다. 강의의 `kill -9 PID`는 SIGKILL을 사용해 무한 루프를 강제로 종료하는 예시이며, 정리 작업을 수행할 기회를 주지 않는다는 차이가 있습니다.

강의 제목에는 `pkill`도 등장합니다. 보충하면 `kill`이 PID를 기준으로 하는 데 비해 `pkill`은 프로세스 이름 등의 조건을 기준으로 시그널을 보낼 수 있습니다. 여러 프로세스가 함께 맞을 수 있으므로 이름을 확인하지 않고 사용하지 않습니다.

## 6. 우선순위와 모니터링

### nice / renice

- nice 값 범위: **-20 ~ 19**.
- 값이 작을수록 일반적인 스케줄링에서 우선순위가 높습니다.
- 기본 nice 값은 보통 0입니다.
- 일반 사용자는 통상 자신의 작업의 nice 값을 늘려 우선순위를 낮출 수 있고, 값을 줄이는 데에는 추가 권한이 필요합니다.

~~~bash
nice -n 13 ./infinite_loop &
ps -el
renice 15 PID
ps -el
~~~

`PID`는 실습 프로세스의 실제 번호로 바꿉니다. `nice`는 새로 실행할 때 값을 지정하고, `renice`는 이미 실행 중인 프로세스의 값을 변경합니다. 강의의 관찰 예시는 NI가 13으로 시작하거나 0에서 15로 바뀌는 모습입니다.

### top / htop

`ps`는 특정 시점의 상태를 보지만, `top`과 `htop`은 실시간 모니터링에 적합합니다. **htop**은 Hisham Muhammad가 만든 Hisham's top이며, ncurses 기반의 터미널 인터페이스로 프로세스와 자원 사용을 관찰하고 조작할 수 있습니다.

~~~bash
htop
~~~

강의는 명령이 없을 때 `sudo apt-get install htop`으로 설치하도록 안내합니다. 설치는 본인 실습 VM에서만 수행하는 별도 단계입니다.

## 7. 실행 파일과 GCC 실습

실행 파일에는 운영체제가 해석할 수 있는 형식과 실행 정보가 필요합니다.

- Linux: **ELF(Executable and Linkable Format)**.
- Windows: **PE(Portable Executable)**, `.exe`·`.dll` 등.
- macOS: **Mach-O(Mach Object File Format)**.

서로 다른 운영체제의 실행 형식과 실행 환경은 일반적으로 그대로 호환되지 않습니다. 파일 확장자만 바꿔 다른 운영체제에서 실행하는 것도 불가능합니다.

셸에 외부 프로그램의 상대·절대 경로를 입력하면 커널에 실행을 요청합니다. 강의는 파일 시그니처를 통한 식별과 exec 계열의 실행을 설명합니다. 실행 권한과 지원하는 형식도 필요합니다. `ls`, `cat` 등은 `/bin/ls`, `/usr/bin/cat` 같은 경로의 실행 파일이며, 이름만 입력할 때 경로를 찾는 원리는 다음 [환경 변수](06_environment_variables.md)에서 다룹니다.

### 컴파일과 인터프리터

- **컴파일**: 소스 코드를 실행 가능한 형태로 변환하는 과정.
- 강의의 컴파일 언어 예: C, C++, Go, Java, Rust.
- 강의의 인터프리터 언어 예: Python, JavaScript. 이를 실행하는 인터프리터/런타임 자체는 실행 프로그램입니다.
- 이 구분은 입문용 모델입니다. Java는 보통 바이트코드와 JVM을 사용하고, Python·JavaScript 구현에도 컴파일이나 JIT 단계가 있을 수 있어 “컴파일 언어는 모두 곧바로 OS 네이티브 실행 파일”이라고 단정하지 않습니다.

### Hello, World!

실습용 `hello.c`:

~~~c
#include <stdio.h>

int main(void) {
    printf("Hello, World!\n");
}
~~~

~~~bash
cd ~/Desktop
gcc -o hello hello.c
./hello
~~~

- `gcc`는 GNU Compiler Collection입니다.
- `-o hello`는 출력 파일 이름을 지정합니다.
- `hello.c`를 컴파일하면 `hello`라는 실행 파일이 생성됩니다.
- `./hello`는 현재 디렉터리의 프로그램을 실행하며 `Hello, World!`를 출력합니다.
- `gcc`가 없다면 강의는 Ubuntu에서 `sudo apt update -y` 후 `sudo apt install gcc -y`로 설치하도록 안내합니다.
