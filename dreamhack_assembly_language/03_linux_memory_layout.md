# Dreamhack Assembly Language — Linux 메모리 레이아웃

## 1. 강의 목표

리눅스에서 실행 중인 프로세스는 독립된 가상 주소 공간을 받고, 운영체제는 이 공간을 용도와 권한에 따라 여러 영역으로 나눈다. 이 강의의 목표는 코드·데이터·BSS·힙·스택이 어떤 데이터를 담고 왜 서로 다른 권한을 갖는지 이해하는 것이다.

```text
높은 주소
+---------------------------+
| Stack                     |  함수 프레임, 지역 변수, 반환 주소
|          ↓ 성장           |
|                           |
|          ↑ 성장           |
| Heap                      |  동적 할당
+---------------------------+
| BSS                       |  0으로 초기화되는 전역/정적 데이터
+---------------------------+
| Data / rodata             |  초기화된 전역 데이터 / 읽기 전용 상수
+---------------------------+
| Text(Code)                |  실행할 기계어
+---------------------------+
낮은 주소
```

실제 주소 배치에는 공유 라이브러리, `mmap` 영역, 로더, vDSO 등이 추가되며 ASLR에 의해 실행마다 위치가 달라질 수 있다. 위 그림은 핵심 개념을 위한 단순화다.

## 2. 세그먼트와 메모리 권한

세그먼트는 적재되는 데이터의 용도별로 메모리를 나눈 구획이다. 리눅스 페이지에는 대표적으로 다음 권한을 조합해 부여한다.

- `r`: 읽기(Read)
- `w`: 쓰기(Write)
- `x`: 실행(Execute)

영역을 나누면 코드에는 실행 권한을 주되 쓰기를 막고, 변경 가능한 데이터에는 읽기·쓰기만 허용하는 식으로 최소 권한을 적용할 수 있다. 일반적으로 한 페이지에 쓰기와 실행을 동시에 주지 않는 W^X 원칙은 코드 주입 공격을 어렵게 만든다.

| 영역 | 저장 내용 | 일반 권한 | 대표 예 |
|---|---|---|---|
| Text/Code | 실행 가능한 기계어 | `r-x` | `main`, 사용자 함수 |
| rodata | 변경하면 안 되는 상수 | `r--` | 문자열 리터럴, `const` 상수 |
| Data | 초기화된 변경 가능 전역·정적 데이터 | `rw-` | `int count = 1;` |
| BSS | 초기값이 없거나 0인 전역·정적 데이터 | `rw-` | `int count;` |
| Heap | 실행 중 동적 할당한 데이터 | `rw-` | `malloc`, `calloc` 결과 |
| Stack | 함수 호출에 필요한 임시 상태 | `rw-`, 보통 NX | 지역 변수, 저장 레지스터, 반환 주소 |

## 3. 코드 세그먼트

코드 세그먼트는 CPU가 실행할 기계어가 위치하며 텍스트 세그먼트라고도 부른다. 코드를 읽고 실행해야 하므로 보통 `r-x`이고, 실행 중 임의 수정되지 않도록 쓰기 권한은 제거한다.

NASM에서는 실행할 코드를 `.text` 섹션에 둔다.

```asm
section .text
global _start

_start:
    mov eax, 60      ; x86-64 Linux exit syscall
    xor edi, edi     ; status = 0
    syscall
```

ELF 파일의 **섹션(section)**은 링커 관점의 분류이고, 실행 시 메모리에 매핑되는 **세그먼트(segment)**는 로더 관점의 분류다. 학습 초반에는 `.text`가 실행 가능한 코드 영역으로 매핑된다고 이해하면 충분하지만 둘은 엄밀히 같은 용어는 아니다.

## 4. Data와 rodata

컴파일 시점에 초기값이 정해진 전역·정적 데이터가 위치한다.

```c
int data_num = 31337;                       // 쓰기 가능한 data
char data_rwstr[] = "writable_data";        // 배열 내용은 data
const char data_rostr[] = "readonly_data";  // 보통 rodata
char *str_ptr = "readonly";                 // 포인터는 data, 리터럴은 rodata
```

마지막 줄은 자주 헷갈린다.

- `str_ptr`이라는 포인터 변수 자체는 변경 가능한 전역 변수이므로 data에 있다.
- 포인터가 가리키는 문자열 리터럴은 일반적으로 rodata에 있다.
- `str_ptr = other;`처럼 포인터 값을 바꾸는 것은 가능하지만, `str_ptr[0] = 'R';`로 문자열 리터럴을 수정하려 하면 잘못된 메모리 접근이 될 수 있다.

NASM에서는 초기화된 데이터를 `.data`에, 명시적 읽기 전용 데이터를 `.rodata`에 정의할 수 있다.

## 5. BSS

BSS(Block Started by Symbol)는 초기화되지 않았거나 0으로 초기화되는 전역·정적 변수를 위한 영역이다.

```c
int bss_data;

int main(void) {
    printf("%d\n", bss_data);  // 프로그램 시작 시 0
}
```

실행 파일 안에 큰 0 배열의 모든 바이트를 그대로 저장할 필요 없이 “이 크기만큼 0으로 초기화할 공간이 필요하다”는 정보만 기록할 수 있어 파일 크기를 줄인다.

NASM 예시:

```asm
section .bss
buffer resb 4096
count  resq 1
```

## 6. 스택 세그먼트

스택은 LIFO 방식의 메모리 영역으로, 함수 호출과 함께 생성되는 스택 프레임에 다음 정보가 놓일 수 있다.

- 지역 변수와 임시 값
- 스택으로 전달되는 함수 인자
- 호출자가 저장한 레지스터
- 이전 프레임 포인터
- 반환 주소

x86/x86-64의 스택은 일반적으로 높은 주소에서 낮은 주소 방향으로 자란다. `rsp`가 현재 최상단을 가리키며 `push`는 `rsp`를 감소시키고 값을 저장한다.

### 전형적인 프롤로그와 에필로그

32비트 예시:

```asm
; prologue
push ebp
mov  ebp, esp
sub  esp, 0x100

; ... 함수 본문 ...

; epilogue
mov  esp, ebp
pop  ebp
ret
```

`mov esp, ebp; pop ebp`는 `leave` 한 명령으로 표현할 수 있다.

64비트에서는 `rbp`, `rsp`를 사용한다. 최적화된 함수는 프레임 포인터를 생략할 수 있으므로 모든 함수가 반드시 같은 프롤로그를 갖는 것은 아니다.

### NX와 보안

과거에는 스택에서 코드를 실행할 수 있는 환경이 있었지만, 스택에 셸코드를 넣고 실행하는 공격이 널리 알려지면서 현대 시스템은 보통 스택을 실행 불가(NX)로 매핑한다. NX는 코드 실행을 막지만 스택의 반환 주소 등 제어 데이터를 덮어쓰는 문제 자체를 제거하지는 않으므로 ROP 같은 공격이 등장한다.

## 7. 힙 세그먼트

힙은 실행 중 필요한 크기의 메모리를 동적으로 할당하는 영역이다.

```c
int *heap_data_ptr = malloc(sizeof(*heap_data_ptr));
*heap_data_ptr = 31337;
printf("%d\n", *heap_data_ptr);
free(heap_data_ptr);
```

- `heap_data_ptr`가 지역 변수라면 포인터 자체는 스택에 있을 수 있다.
- `malloc`이 반환한 주소가 가리키는 실제 객체는 힙에 있다.
- 할당과 해제를 잘못 관리하면 Use-After-Free, Double Free 같은 취약점이 발생한다.

리눅스 메모리 할당기는 필요할 때 `brk` 계열이나 `mmap` 시스템 콜을 이용해 커널로부터 주소 공간을 확보한다. 모든 `malloc` 호출이 즉시 시스템 콜 1회와 정확히 대응하는 것은 아니며, 사용자 공간 할당기가 확보한 큰 영역을 재사용한다.

힙은 전통적인 그림에서 낮은 주소에서 높은 주소로, 스택은 반대 방향으로 자란다. 서로 반대 방향으로 배치하면 두 동적 영역이 남은 가상 주소 공간을 효율적으로 사용할 수 있다.

## 8. 메모리에서 변수 위치 추론하기

```c
int global_init = 7;        // data
int global_zero;            // bss
const char *msg = "hello"; // msg 포인터: data, 문자열: rodata

int main(void) {
    int local = 3;          // 보통 stack 또는 최적화 시 register
    char *p = malloc(32);   // p: stack/register, 가리키는 버퍼: heap
    free(p);
}
```

컴파일러 최적화로 인해 지역 변수가 레지스터에만 머무르거나 상수가 코드에 직접 삽입될 수 있다. “C 문법상 이 종류이므로 반드시 이 주소에 있다”가 아니라 **전형적인 배치 규칙**으로 이해하고, 실제 바이너리는 `readelf`, `objdump`, GDB의 `vmmap` 등으로 확인한다.

---

## 9. GDB에서 확인할 포인트

```gdb
start
vmmap
info registers
x/16gx $rsp
disassemble main
```

- `vmmap`: 주소 범위, 권한, 매핑된 파일을 확인한다.
- `x/16gx $rsp`: 스택 최상단부터 8바이트 단위로 값을 확인한다.
- `disassemble`: 코드 영역의 기계어를 어셈블리어로 읽는다.

## 핵심 체크

- 코드와 데이터는 용도뿐 아니라 권한도 다르다.
- 초기화된 전역 변수는 data, 초기화되지 않은 전역 변수는 BSS에 위치하는 것이 전형적이다.
- 포인터 변수의 위치와 포인터가 가리키는 객체의 위치는 서로 다를 수 있다.
- 스택은 보통 낮은 주소 방향, 힙은 높은 주소 방향으로 확장된다.
- 프롤로그·에필로그와 반환 주소를 이해하면 함수 호출과 스택 취약점 분석이 쉬워진다.
