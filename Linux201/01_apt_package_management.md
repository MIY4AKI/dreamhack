## 1. 패키지와 의존성

패키지는 프로그램을 실행하는 데 필요한 파일을 하나의 설치 단위로 묶은 것이다. 실행 파일뿐 아니라 설정 파일과 라이브러리도 포함될 수 있다. 많은 프로그램과 버전을 사람이 일일이 관리하기 어려워 **패키지 관리자**를 사용한다. Ubuntu에서는 APT(Advanced Package Tool)를 주로 사용한다.

### 소스 패키지와 바이너리 패키지

- **소스 패키지**: 소스 코드를 제공한다. 사용자가 직접 컴파일하므로 시간이 걸리고 빌드 오류가 발생할 수 있다. 대신 소스를 수정해 원하는 기능이나 형태로 바꿀 수 있다.
- **바이너리 패키지**: 이미 컴파일된 프로그램을 제공한다. 보통 더 빠르고 간편하게 설치할 수 있지만, 필요한 라이브러리 등 의존성 파일이 없으면 실행되지 않을 수 있다.

예를 들어 프로세스 모니터 `htop`은 터미널 화면 처리를 위한 `ncurses` 계열 라이브러리를 사용한다. 다른 패키지나 라이브러리가 필요하다는 관계가 **패키지 의존성**이다. 강의의 `ncurse` 표기는 이 라이브러리를 가리킨다.

패키지 관리자는 설치 대상과 그 의존성을 함께 파악한다. 이 덕분에 사용자가 모든 의존성을 직접 설치하는 부담을 줄일 수 있으며, 일반적인 배포판에서는 바이너리 패키지를 많이 사용한다.

## 2. 패키지 관리 도구의 두 수준

### 저수준 도구

- Debian/Ubuntu 계열: `dpkg`
- Red Hat 계열: `rpm`
- 개별 패키지 파일의 설치·제거를 다룬다. 필요한 의존성을 저장소에서 자동으로 찾아 설치하는 역할은 고수준 도구에 맡긴다.

### 고수준 도구

- Debian/Ubuntu 계열: `apt`, `apt-get`
- Red Hat 계열: `yum`, `dnf`
- 저장소와 의존성 관계를 이용해 필요한 패키지를 함께 찾아 설치한다.
- 일반 사용자는 대체로 고수준 도구를 사용한다.

Ubuntu는 Debian 계열이므로 이 강의에서는 `apt`를 기준으로 설명한다.

## 3. apt와 apt-get

`apt-get`이 먼저 등장했다. 패키지 설치·업데이트·제거는 `apt-get`, 패키지 검색·조회는 `apt-cache`, 설치된 패키지 목록 확인은 `dpkg -l`처럼 여러 도구로 나누어 처리했다. `apt`는 이 도구들의 자주 쓰는 기능을 사용자 친화적인 인터페이스로 모은 명령이다.

- `apt`: 사람이 터미널에서 사용하기 편한 일반적인 관리 작업에 적합하다.
- `apt-get`: 세부적인 옵션과 기존 관리 절차를 활용하는 데 유용하다.

강의는 일반 사용자에게 `apt`의 기능만으로 충분한 경우가 많다고 설명한다. 설치·제거·저장소 업데이트 등 시스템을 변경하는 작업은 보통 root 권한이 필요하므로 `sudo`를 붙인다. 단순한 검색·조회는 일반 사용자로도 가능하다.

## 4. 명령과 옵션

기본 형태는 다음과 같다. 명령별로 인수와 사용할 수 있는 옵션이 달라진다.

```bash
apt [옵션] [명령] [대상]
```

### 강의에서 다루는 명령

- `apt list`: 조건에 맞는 패키지 목록을 출력한다.
- `apt search <검색어>`: 패키지를 검색한다.
- `apt show <패키지>`: 패키지 설명·버전·의존성 등의 정보를 확인한다.
- `sudo apt install <패키지>`: 설치한다.
- `sudo apt reinstall <패키지>`: 재설치한다.
- `sudo apt remove <패키지>`: 제거한다. 설정 파일이 남을 수 있다.
- `sudo apt update`: 저장소의 패키지 **목록/색인 정보**를 갱신한다. 설치된 프로그램을 업그레이드하는 명령이 아니다.
- `sudo apt upgrade`: 갱신된 목록을 바탕으로 설치된 패키지를 업그레이드한다. 의존성이나 보류 조건에 따라 모든 패키지가 반드시 바뀌는 것은 아니다.

### 강의에 등장하는 옵션

- `-d`: 설치하지 않고 다운로드만 한다.
- `-y`: 확인 질문에 자동으로 yes로 답한다. 실제 변경 사항을 확인하려면 처음에는 생략하는 편이 안전하다.
- `--upgradable`: `apt list --upgradable`처럼 업그레이드 가능한 패키지를 조회한다.
- `--only-upgrade`: 설치 명령과 함께 사용하면 이미 설치된 패키지의 업그레이드만 수행한다.
- `--dry-run`: 실제 변경 없이 예상 작업을 확인한다.
- `--purge`: 제거할 때 패키지의 설정 파일도 제거한다.
- `--fix-missing`, `--arch-only`: 강의의 옵션 표에도 등장하지만, 원문의 단순화된 설명을 그대로 일반화해서 사용하면 안 된다.

> **보충/정정 — 두 옵션의 정확한 의미**  
> `--fix-missing`은 다운로드할 수 없거나 무결성 검사를 통과하지 못한 패키지를 보류하고 나머지를 처리하는 옵션이다. 깨진 의존성을 자동으로 모두 복구하는 `--fix-broken`과 다르다. `--arch-only`는 아키텍처에 의존하는 **빌드 의존성**만 처리하는 `apt-get` 옵션으로, 일반 설치에서 특정 CPU용 패키지만 선택한다는 뜻이 아니다. 사용하려는 명령·버전의 `man apt`, `man apt-get`을 확인한다. [Debian APT 공식 매뉴얼](https://manpages.debian.org/testing/apt/apt-get.8.en.html)

### 업데이트 실습 흐름

강의에서 제시한 준비 명령은 다음과 같다.

```bash
sudo apt update -y && sudo apt upgrade -y
```

`&&`는 앞의 명령이 성공했을 때 다음 명령을 실행한다. 처음에는 다수의 패키지가 업그레이드될 수 있고, 이미 최신 상태이면 변경할 패키지가 없다는 출력이 나타난다.

> 저장소 목록 갱신과 전체 시스템 업그레이드는 서로 다른 작업이다. 매번 프로그램 하나를 설치하기 전에 전체 업그레이드가 반드시 필요한 것은 아니다. 강의 명령은 실습 환경의 준비 과정이며, 실제 시스템에서는 변경될 패키지를 먼저 확인한다.

## 5. gdb-multiarch 설치·실행·제거

강의는 여러 아키텍처를 지원하는 디버거 패키지로 설치 과정을 보여 준다.

```bash
# 정보 확인
apt show gdb-multiarch

# 설치
sudo apt install gdb-multiarch

# 실행
gdb-multiarch
```

제공된 VM에 이미 설치되어 있다면 설치 명령을 실행해도 새로 다운로드하지 않는 화면이 나올 수 있다. 실행되면 디버거 프롬프트가 표시된다. 강의에서는 `Ctrl+D`로 디버거를 종료한다.

```bash
# 제거 — 확인 질문의 Y/n을 읽고 선택
sudo apt remove gdb-multiarch

# 다시 설치
sudo apt install gdb-multiarch
```

제거 후 다시 설치하면 이전과 달리 실제 다운로드·설치 단계가 나타난다. 제거 명령에 `-y`를 붙이면 `Y/n`에 직접 답하는 과정 없이 진행된다. `remove`와 설정 파일까지 지우는 `purge`의 차이도 구분한다.

## 6. 업데이트 오류 대응

### Release 파일이 아직 유효하지 않다는 오류

강의의 예시는 Docker 저장소의 `InRelease` 파일이 `not valid yet`라고 나오는 경우다. 시스템의 날짜·시간이 실제 시간과 맞지 않아 저장소 파일의 유효 시점을 미래로 판단할 수 있다.

- 일반 Ubuntu에서는 실제 날짜·시간 및 동기화를 점검한다.
- WSL에서는 Windows와 WSL의 시간 동기화 문제를 확인한다.
- 강의가 제시한 WSL 재시작 방법: WSL에 연결된 VS Code, Ubuntu 터미널 등 모든 창을 종료하고, Windows PowerShell에서 다음 명령을 실행한 뒤 WSL을 다시 연다.

```powershell
wsl --shutdown
```

이 명령은 실행 중인 WSL 배포판을 종료한다. 실행 전 작업을 저장해야 한다. 강의의 관련 참고 글은 [APT의 Release file is not yet valid 오류](https://askubuntu.com/questions/1096930/sudo-apt-update-error-release-file-is-not-yet-valid)다.

### DNS 이름 해석 실패

`Temporary failure resolving 'packages.microsoft.com'`처럼 이름을 IP로 해석하지 못하는 오류가 나면 DNS 설정이나 네트워크 연결을 점검한다. 강의는 `nameserver` 설정 문제의 예시로 아래 명령을 제시한다.

```bash
echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf > /dev/null
sudo apt update -y && sudo apt upgrade -y
```

- `tee`가 관리자 권한으로 파일을 쓴다.
- `> /dev/null`은 화면에 다시 출력될 내용을 버린다.
- 첫 명령은 기존 `/etc/resolv.conf` 내용을 **덮어쓴다**.

> 위 명령은 강의의 특정 실습 환경에서 제시된 대응이다. 이름 해석 실패가 항상 잘못된 `nameserver` 때문인 것은 아니다. 관리형 DNS 설정이나 WSL의 자동 생성 파일에 무조건 적용하면 기존 설정을 잃거나 다시 덮어써질 수 있다. 기존 설정과 연결 상태부터 확인한다. 인증서·저장소 서명 검증을 끄는 방식으로 해결하지 않는다.

## 7. 복습 체크

- [ ] 실행 파일 외에 패키지가 포함할 수 있는 파일을 설명할 수 있다.
- [ ] 소스/바이너리 패키지의 장단점과 의존성을 구분한다.
- [ ] `dpkg`와 `apt`의 역할 차이를 안다.
- [ ] `update`는 목록 갱신, `upgrade`는 설치된 패키지 업그레이드임을 구분한다.
- [ ] 조회 → 설치 → 실행 → 종료 → 제거 → 재설치 흐름을 이해한다.
- [ ] `-y`, `--dry-run`, `--only-upgrade`, `--purge`가 변경 범위에 미치는 영향을 안다.
- [ ] 시간 오류와 DNS 오류를 출력 메시지로 구분하고, 환경에 맞게 대응한다.

패키지 관리는 Windows의 프로그램 설치·제거에 대응하는 일상적인 리눅스 작업이다. 프로그램을 원하는 환경에서 정상적으로 설치하고 실행하려면 명령뿐 아니라 의존성과 오류 메시지의 의미를 함께 이해해야 한다.
